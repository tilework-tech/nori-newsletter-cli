# Noridoc: nori-newsletter-cli

Path: @/

### Overview

- CLI tool for managing and sending newsletters via AWS SES, built with Commander and TypeScript
- Provides both low-level SES operations (contact management, sending, suppression, templates, identities, config sets, validation, bulk import/export jobs) and high-level abstraction commands (`health` dashboard, `preflight` pre-send checks, `cleanup` contact/suppression reconciliation, `setup` infrastructure provisioning, `reputation` sending health analysis, `domain-check` DNS/deliverability diagnostics, `audit` comprehensive account readiness assessment, `send-safe` atomic preflight+filter+send) that compose multiple service calls and/or external lookups into newsletter-specific workflows
- Sends emails concurrently with automatic rate throttling based on the account's SES sending quota. The `send` command sends individually via `SendEmail`; the `bulk-send` command batches up to 50 recipients per API call via `SendBulkEmail`
- Published to npm as `nori-newsletter-cli`, installable globally via `npm install -g nori-newsletter-cli`

### How it fits into the larger codebase

- Entry point is `@/src/index.ts`, which wires up the SES client, output, config, and Commander program
- All CLI commands live in `@/src/commands/` and are registered in `@/src/program.ts`
- AWS SES operations are abstracted behind the `SesService` interface in `@/src/services/ses.ts`, making commands testable with a mock implementation
- Shared utility functions (email parsing, validation, CSV parsing, HTML extraction) live in `@/src/lib/` and are used directly by commands
- Configuration is loaded from `newsletter.config.json` in the working directory via `@/src/config.ts`
- Tests in `@/tests/` mirror the `src/` directory structure and use a shared mock harness in `@/tests/helpers.ts`

### Core Implementation

- **Build pipeline:** TypeScript compiles `src/` to `dist/` via `tsc`. The `dist/index.js` entry point has a `#!/usr/bin/env node` shebang for CLI execution
- **npm publishing:** The `files` array in `package.json` ships `dist/`, `src/`, `LICENSE`, and `README.md`. The `prepublishOnly` script runs `npm run build && npm test` as a safety gate before every publish. Publishing is automated by `.github/workflows/publish.yml`, which publishes to npm when a **GitHub Release is published** (using the `NPM_TOKEN` repo secret). This is the supported release path; the version in `package.json` and the `--version` in `@/src/program.ts` must be bumped in lockstep before each release, because `npm publish` refuses to overwrite an existing version. This exists because a stale published package (built before the resume feature and never version-bumped) worsened the original duplicate-send incident
- **Module system:** Uses ESM (`"type": "module"`) with Node16 module resolution. All internal imports use `.js` extensions per Node ESM requirements
- **Dependency injection:** `@/src/index.ts` constructs concrete dependencies (SES client, output, config loader) and passes them to `createProgram()`. Tests substitute mocks at this same boundary. The SES client is configured with `maxAttempts: 5` for SDK-level retry on transient errors. `createProgram()` also accepts an optional 4th `options` parameter for non-SES external dependencies: `dnsResolver` for the `domain-check` and `audit` commands, and `launchDetached` (a `DetachLauncher` from `@/src/lib/detach.ts`) for the `--detach` mode on `send`/`send-safe`/`bulk-send`. In production the resolver defaults to Node's `dns.promises` and the launcher to `defaultDetachLauncher`; in tests mocks are injected via this parameter
- **Send throttling:** `send` (`@/src/commands/send.ts`), `send-safe` (`@/src/commands/send-safe.ts`), and `bulk-send` (`@/src/commands/bulk-send.ts`) all query `SesService.getMaxSendRate()` before each send run, then use `p-throttle` to cap concurrent sends at 80% of the account's max rate (minimum 1/sec). `send` and `send-safe` throttle per-recipient; `bulk-send` throttles per-batch (batch = 50 recipients). All three use `Promise.allSettled` so individual failures do not abort the run. This prevents SES `ThrottlingException` errors that would otherwise silently drop emails
- **Resumable, detachable sends:** all three send commands share the durable progress journal in `@/src/lib/send-journal.ts` and the detach helper in `@/src/lib/detach.ts`. Each successful delivery is `fsync`'d to a journal under the durable per-user state dir (`$XDG_STATE_HOME/nori-newsletter/`, fallback `~/.local/state/nori-newsletter/`), so re-running the same command after an interruption skips already-sent recipients (shared `--no-resume` / `--state-file` options). `--detach` re-execs the CLI as a detached background process logging to that state dir, so a long send is never held in a foreground shell. Both behaviors exist to prevent a duplicate-send incident: an interrupted send must never re-blast the whole list on restart (see `@/src/lib/docs.md`)
- **Open/click tracking:** `newsletter.config.json` accepts an optional `configurationSetName` (`@/src/config.ts` -- optional on purpose, so configs written before this feature keep loading). When present, `send`, `send-safe`, and `bulk-send` attach that SES configuration set (the thing that makes SES emit open/click events) plus per-issue message tags `campaign=<sanitized html filename>` and `source=newsletter`, so an open event can be attributed to a specific issue. `bulk-send` has no HTML file, so it derives the campaign id from the template name. Tag derivation and the SES tag charset rules live in `@/src/lib/campaign.ts`. When the field is absent, no configuration set and no tags are sent (tags are meaningless without a config set) and each send command prints one warning line to stderr per run -- never a hard error. The campaign id is also printed in `--dry-run` output so it can be inspected without sending
- **Help output:** `@/src/program.ts` uses Commander's `addHelpText('after', ...)` to append a self-contained Configuration section to `--help`, documenting all required config fields, an example `newsletter.config.json`, and the required AWS environment variables. This keeps the help output usable without external docs

### Things to Know

- The `engines` field requires Node >= 18.0.0, matching the ES2022 target in `tsconfig.json`
- The package is CLI-only (no `main`/`exports` — the entry point has top-level side effects). Consumers use it through the `bin`-registered `nori-newsletter` command
- Source files (`src/`) are included in the published package alongside compiled output (`dist/`) for source map debugging and transparency
- The `SesService` interface (`@/src/services/ses.ts`) includes `getMaxSendRate()`, which calls `GetAccountCommand` to read the account's `SendQuota.MaxSendRate`. It falls back to 1/sec on any error or missing quota, treating the safest rate as default
- The send command makes an additional AWS API call (`GetAccountCommand`) before each send run to determine the throttle rate
- Several commands operate at the AWS account level and do not depend on `newsletter.config.json`: `suppression`, `lists`, `stats`, `templates`, `identities`, `config-sets`, `validate check`, `reputation`, and most `jobs` subcommands. Their factory functions still accept `getConfig` for consistency with the shared command factory signature. The `jobs import-contacts` subcommand defaults to the configured `contactListName` when `--list` is not provided. The abstraction commands that depend on config are `health`, `preflight`, `cleanup`, `setup`, `domain-check`, `audit`, `send-safe`, and `validate list`. Note that `reputation` is an abstraction command but operates account-level only. `domain-check` and `audit` extract the domain from the configured `fromAddress` by default but can be overridden with `--domain`
- The abstraction commands (`health`, `preflight`, `cleanup`, `setup`, `reputation`, `domain-check`, `audit`, `send-safe`) are a distinct architectural layer: they compose existing `SesService` methods (and in the case of `domain-check` and `audit`, external DNS lookups) without adding new AWS API calls. They exist because SES treats suppression lists and contact lists as separate systems with no cross-referencing, has silent failure modes (suppressed addresses still count toward quota), requires multiple API calls to assemble a complete picture of newsletter health or provision the required infrastructure, provides raw metric numbers without interpreting them against enforcement thresholds, and generates DKIM tokens without verifying that the corresponding DNS records actually exist. The `audit` command is the culmination of the read-only check layer -- it composes all the checks from `health`, `reputation`, `domain-check`, `setup`, and `cleanup` into a single report with a unified exit code. The `send-safe` command is the culmination of the send layer -- it composes preflight checks, suppression filtering, and email sending into a single atomic operation
- The `bulk-send` command uses `SendBulkEmail`, which does **not** support `ListManagementOptions` (the SES feature that auto-injects unsubscribe links). Because of this, `bulk-send` fetches opted-in contacts client-side via `listContacts` instead of relying on SES-managed unsubscribe filtering. This is a known AWS API limitation, not a design oversight
- The `stats send` subcommand and `reputation` command require VDM (Virtual Deliverability Manager) to be enabled on the SES account for full metrics. VDM data is retained for 60 days, which caps the `--days` option at 60. The `reputation` command degrades gracefully when VDM is unavailable, displaying a fallback message instead of failing
